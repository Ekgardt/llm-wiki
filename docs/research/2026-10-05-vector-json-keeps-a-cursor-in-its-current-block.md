# Vector JSON keeps a cursor in its current block

Research date: 2026-10-05. Qualification candidate, not installed.

The closed vector format is streamed into an owned ephemeral SQLite lookup. Its reader currently slices off the remaining buffer after every delimiter and scalar. This copies unrelated upcoming values repeatedly. The selected change retains a cursor in the current text block and compacts consumed text only when it reads the next block. It keeps the existing 64 KiB transport reads, decoder, closed flat schema, duplicate-field and duplicate-ID refusal, row-count and artifact-hash validation, cancellation and cleanup. No filesystem or generation-validity verdict is cached. It introduces no dependency, persistent artifact, schema, directory, environment setting or budget.

Three independent primary sources fetched today:

- Python 3.10.22 JSON documentation and implementation: https://docs.python.org/3.10/library/json.html and https://github.com/python/cpython/blob/v3.10.22/Lib/json/decoder.py. The decoder accepts an index into the same input string and reports the ending index; JSON decoding is not itself a framed streaming protocol. A scalar at the end of an unfinished block must still wait for more text, so a number split between blocks is not accepted prematurely.
- IETF RFC 8259, current Internet Standard: https://datatracker.ietf.org/doc/html/rfc8259. Arrays preserve order; JSON whitespace, escaped strings, numbers and complete framing must remain intact. The initial rfc-editor URL could not be fetched; the IETF publication was fetched successfully.
- SQLite transaction documentation: https://www.sqlite.org/lang_transaction.html. The existing temporary lookup is still committed only after complete validated parsing. A parser exception must close and remove the temporary state; incomplete results are not successful metadata.

Alternatives rejected: whole-document `json.load` (materializes all arrays), a new third-party parser (unnecessary dependency), larger arbitrary read blocks (retains repeated-copy behavior), trusting an earlier filesystem or source verdict (stale-authority risk), and accepting only selected fields (weakens complete validation). The cursor still requires rescanning an unfinished unusually large scalar when a block arrives; this change does not claim a general streaming JSON parser or impose a new scalar length ceiling.

The regression counts characters copied by actual string slices while consuming one already-loaded array. Its bound comes from reading framing characters, rather than imposing a production data limit. The original implementation must fail this resource-amplification check while values remain identical. Separate tests exercise numbers and escaped Unicode over tiny reads and one scalar spanning the existing transport block. Existing malformed/trailing/duplicate/cancellation tests remain unchanged. Actual metadata performance and normal dense-search timing must be measured before claiming a repaired query.

Evidence: eight exact fresh stdio snippets in private `logs/audit-2026-10-05-step7-vector-json-cursor-native-navigation.json`, verified against current ROOT source SHA. The overall code graph is partial and was supplemented with source inspection. The active real generation has 126,298 chunks; its `vectors.json` is used for readonly qualification, never rewritten by this candidate.

Qualification: the unchanged old reader copied 1,769,984 characters while consuming a 13,824-character array; its value and ten boundary controls passed. The cursor passes all eleven checks. Existing vector reuse, schema, seals, freshness and driver checks together pass 46 tests. Actual Lizard and AST checks include every changed callable, nested function and lambda; maximum CCN is 5, with at most two if statements and two nested control levels.

Two sequential readonly parser trials used the identical complete real artifact (SHA-256 619ff932d6333d3a8c95851f4ce56ed2d6479fb369af6c96b624632c836b978f). The old reader took 3.1090 seconds and the cursor 2.8089 seconds. All four 126,298-row columns, every scalar and the complete ordered metadata digest matched; both peaked at 71,344 KiB RSS. Trial order and shared machine load limit performance conclusions. This removes demonstrated copy amplification; it does not establish normal dense-query completion or full-cycle improvement.

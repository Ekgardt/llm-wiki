# Reducer cache uses the state byte budget

Research date: 2026-09-30. A valid checkpoint commit adding the 129th reducer evicted the first solely by entry count. The remaining state was only 36432 bytes against its established 196608-byte budget. Replaying an already observed event then added one duplicate pending checkpoint. This reproduces the mechanism; the installed state currently has six reducers, so it is not evidence of an observed live 129-project loss.

Remove the unmeasured MAX_CHECKPOINT_REDUCERS and its replacement-specific trim helper. State serialization already evicts the same disposable reducer/dedupe caches by actual encoded bytes, preserving its existing 192 KiB target beneath health readers' 256 KiB ceiling. It remains a cache, and byte-budget eviction can still discard old dedupe state; no authority, journal history or pending work is removed by this change. No numerical replacement or operator contract is added.

Primary sources verified today: [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/) describes eviction under a memory budget; [Python JSON encoding](https://docs.python.org/3/library/json.html) defines actual serialization; [OWASP resource consumption](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/) supports actual resource controls. Redis is a reference, not a runtime dependency. The local budget's basis and reader failure are documented by memory_state.py and state-root regression tests.

Alternatives: raising 128 or adding an unmeasured knob keeps duplicated policy; dropping the byte budget would let readers go blind again; migrating this cache to another database adds unnecessary architecture.

# An idle checkpoint backlog advances on maintenance time

Research date: 2026-10-01. The installed main project holds eight delta-bearing events from 2026-09-29 10:03:35–10:03:55 UTC. Its previous checkpoint is at 10:03:34. The maintenance drain reports zero moved and no failure. Claims are available, no database checkpoint is unfinished, and a read-only replay confirms the plan remains waiting although wall-clock expiry is due. The planner only compares the newest event timestamp, so a quiet project never advances its debounce clock. An independent synthetic eight-event regression reproduces this refusal before a fix, preserving its failure log.

Proposed implementation: the unattended drain supplies its current aware UTC observation time through the existing planning chain. Debounce eligibility compares the later of event time and that observation time. The journal and reducer retain the original last event timestamp; no synthetic event is added. Hook/replay callers without an observation clock keep their existing event-time behavior. Claims, prefix batches, in-flight replay, deadlines and transaction fences continue through the same path. No setting, directory, schema, daemon or environment contract changes.

Primary sources verified today: [Python datetime](https://docs.python.org/3/library/datetime.html) defines aware UTC time and duration arithmetic; [Apache Flink processing-time example](https://nightlies.apache.org/flink/flink-docs-master/docs/learn-flink/event_driven/) distinguishes processing-time expiration from event records; [Redis expiration behavior](https://redis.io/docs/latest/develop/ai/search-and-query/advanced-concepts/expiration/) evaluates validity at read time. These are conceptual references, not dependencies. All implementation remains compatible with Python 3.10 through timezone.utc.

Alternatives rejected: clearing pending events loses evidence; an extra fake session event invents history; waiting for the next event leaves an idle project blocked indefinitely; adding a timer or daemon changes architecture. Use the already installed nightly recovery step. This changes no numerical value and does not establish a new basis for the separate existing 30-second debounce interval. Wall-clock movement can affect eligibility; evidence timestamps remain unchanged and caller deadlines use the existing monotonic clock.

# Source addresses keep their roles without repeating them

Research and qualification date: 2026-10-07. This is an internal derived draft display and dynamic input-schema change. It changes no source partition, physical evidence authority, persisted receipt, environment, path or provider contract.

The installed explicit source-ID menu repeated both labels for every eligible physical line, then enumerated all the same IDs in the draft schema. The unchanged long-entry regression reproduced a refusal on an otherwise legal 16,367-byte physical part: 402 authenticated choices produced a 38,589-byte local serialized request against the existing 27,744 input estimate. The same complete source without the optional address protocol occupied 23,387 bytes. Shorter labels alone could not restore this case.

Addresses now group only consecutive `(source_line, visible FILE LF)` pairs inside one FILE and ENTRY. Both values must increase by exactly one. The endpoints describe a paired, inclusive range; a gap in either component ends it. Singleton labels stay explicit. This preserves every ordered tuple, including repeated timestamps, sparse IDs, multiple FILE blocks and UTF-8 physical parts. Raw selected source and context remain contiguous and unchanged. IDs are still untrusted output, not source authority: original quote, timestamp, hash, span, ambiguity, native-companion and final DLP checks remain necessary.

A denser short-line source exposed the same defect in the full enum after the address table became compact: 1,495 actually eligible choices in a 16,384-byte part still produced 32,498 bytes. The schema therefore chooses the shorter canonical serialization of the complete enum and disjoint integer runs. Singleton runs use const; other runs include their own integer type and inclusive minimum/maximum. Disjoint oneOf runs represent exactly the same allowed set. Missing IDs between runs never become allowed. Small or sparse sets keep the existing enum when it is shorter. The choice is measured serialization size, not an arbitrary threshold. The project's existing validator requires explicit type in each numeric subschema to enforce bounds; a failing negative-control run caught the initially missing type, and remains qualification evidence.

The local validator's strict Python integer contract and the ordinary binder continue to reject booleans, integral floats, nonintegral floats, strings and out-of-scope IDs. Generic JSON Schema treats integral floats as integer values, so this local rule must not be presented as a universal JSON Schema property. The native Codex route's grammar enforcement is not established by API documentation or this no-model qualification.

Alternatives were shorter singleton labels, a fallback legacy-only draft mode, and raising the budget. Short labels did not fix the measured dense case; a separate mode would require more planner/dispatch state; raising the budget would conceal display overhead and leave its basis unqualified. Lossless runs keep one common layout in byte planning, token-adapter planning and final request counting. Range notation can still affect model interpretation; full useful model-cycle quality and all retry/output costs remain required before an efficiency claim. Existing 32,768 target, 4,000 output reservation, 1,024 margin and CLI full-wire/output uncertainty are not qualified by this correction.

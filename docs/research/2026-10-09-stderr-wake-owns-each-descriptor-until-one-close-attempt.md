# A stderr wake closes each owned descriptor once

Investigated on 2026-10-09 after a focused macOS CI failure: the original blocked-cleanup heartbeat test reported background cleanup `OSError`, code 9. The same original test passed locally; the complete original focused set passed 1205 tests with 99 platform/profile skips and no recorded EBADF. The exact cause of the macOS failure is not established by that local result.

Investigation did reproduce a related resource-ownership defect. Cleanup of an unstarted stderr drain calls `_StderrWake.abandon`. Its read descriptor remained an integer after being closed. When another file received that descriptor number, a second cleanup closed the other file. A real-descriptor regression invokes the actual `_stop_stderr_drain` twice and reads the independently owned file between cleanup attempts. It failed before correction. A second causal test closes a descriptor and then reports an uncertain native close: the old code suppressed that error and allowed a later retry against a reused number.

Both pipe ends now transfer ownership under their existing lock before one close attempt. A known successful close is idempotent. An uncertain close is retained as an error and reported on subsequent cleanup without another native close against the old number. The drain thread releases its read end through the same ownership method. Its recorded close uncertainty reaches the joining cleanup, so a stopped thread alone is not reported as complete resource cleanup. Existing lifecycle and fenced ownership remain responsible for retained failed cleanup. This introduces no daemon, runtime path, persistent schema, environment setting, retry count, numerical cap or dependency.

Discarding EBADF, repeating native closes until they appear successful, increasing test deadlines and weakening the original heartbeat assertions were rejected. Descriptor-number reuse makes a repeated raw close unsafe even when a previous close reported failure.

## Primary sources and compatibility

Checked on 2026-10-09: [Python 3.10 OS documentation](https://docs.python.org/3.10/library/os.html#os.close), the maintained [Linux close manual](https://man7.org/linux/man-pages/man2/close.2.html), and Apple's [archived Darwin close manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/close.2.html). The Apple page is a historical primary reference, not evidence that every current macOS detail was verified. Python provides the relevant interface, Linux explicitly discusses descriptor reuse and unsafe close retries, and Apple documents EBADF and EINTR. The concrete choice follows the reproduced ownership error and preserves uncertainty rather than assuming all platforms close identically on error. Python 3.10 compatibility and current platform behavior require direct tests. The Windows path does not create this POSIX wake pipe.

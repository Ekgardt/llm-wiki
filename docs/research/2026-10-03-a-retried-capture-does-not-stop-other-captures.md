# A retried capture does not stop other captures

Research date: 2026-10-03. Installed Python 3.12.3; supported Python 3.10.

Actual private get_architecture caller/callee dispatch against the current installed 0a18550f repository index precedes this design; envelopes and partial flags are retained in logs/audit-2026-10-03-capture-drain-before-architecture.json. This is not a full MCP protocol check. The queue uses the existing adopted Reliability v3 fenced SQLite transitions and at-least-once delivery. No cloud queue, directory, environment contract, daemon, schema or retry policy is added.

The worker durably fails a claimed task, then raises its processor exception. The adapter aborts its entire drain on that exception, so other independently eligible captures wait for another external wake. Source: flush_memory._process_or_fail, integration_adapter._drain_capture_work. Reproduction must use actual temporary adopted queue tasks: the first must retain a named deferred failure and the second must complete through the ordinary processor. A failed settlement or owner release must still abort.

Current independent primary sources checked on the research date:

- [RabbitMQ consumer acknowledgements](https://www.rabbitmq.com/docs/confirms): distinguish acknowledgement from negative acknowledgement; an unacknowledged delivery remains separate from completed work. Its AMQP mechanism is not introduced here.
- [Microsoft Azure Functions queue triggers](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-storage-queue-trigger): failures retry a specific message and exhausted messages enter a poison queue. Azure defaults and infrastructure are not copied.
- [Amazon SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html): isolate repeatedly failing work while retaining it for diagnosis; moving a FIFO message can change ordering. These captures have their existing queue order and backoff; no production task is redriven or removed.

Alternatives: catching every exception in the drain would conceal unsettled leases and ownership failures, so reject it. Always stopping preserves errors but strands unrelated ready captures. Changing exception types globally breaks current callers. Select an optional failure observer at the worker boundary: only after queue.fail commits may the adapter receive the actual processor/exhaustion exception as a settled turn. Default callers retain the raised exception. The observer records the ordinary redacted diagnostic; the return remains an exception object, never a success receipt. Ownership release still runs in finally and can abort the drain. Exhausted work remains explicitly lost, not deferred. No new numeric limit is introduced; existing drain limits remain a separate unresolved law-9 item.

Required evidence: genuine regression before implementation; deferred-state/error-code and subsequent completion; failed settlement abort; exact default exception identity; exhausted diagnostic; ordinary related capture tests; actual Lizard/AST complexity, static analysis and isolated installed verification. No production completion or token improvement is claimed by this design document.

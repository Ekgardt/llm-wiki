# The critic keeps the selected native line

Checked on 2026-10-09. This corrects a reproduced program defect; it does not declare the full operational audit complete.

A native session container can contain many user lines. The immutable claim ledger correctly retains the complete physical container, so different logical citations can have the same byte-span reference. The compiler discarded the draft's evidence-array index during claim derivation, then reconstructed it for the critic by choosing the first matching physical reference. Real drafts selecting indexes 4, 6 or 5 reached the critic as index 0. The critic consequently evaluated a different supporting line. This caused false rejections and correction costs; it does not prove every rejection had this cause.

Three causal tests failed before correction: the actual critique pipeline changed a selected second line to the first; reordering logical citations did not refuse review; a serialized historical claim with ambiguous physical provenance was guessed. The correction retains the validated index and the canonical selected-evidence digest in transient attributes of the compiler's derived claim dictionary. Serialization still emits the existing claim/v1 or claim/v2 fields. No ledger schema, runtime path, environment contract or database changes.

Semantic validation still checks the normalized operation. Critique uses its original, validated claim records to retain their transient citation ownership. Before review, the selected evidence index, physical reference and exact logical evidence digest must agree. Historical records can use a physical reference only when it selects exactly one binding; ambiguity is an explicit refusal. The critique program identity advances to v7, so a v6 reviewed plan cannot bypass the corrected review through the action cache.

Correction feedback can express derived claims using the existing public semantic candidate fields and the preserved evidence index. This is accepted only when rederiving from the same immutable inputs reproduces both the entire canonical ledger record and its selected-citation ownership. Otherwise the full record remains. This removes repeated copies of the complete physical container without deleting supporting context. Complete reviewed quotes can additionally use the existing source_line choices only when exact canonical expansion reproduces every reviewed operation; types, ordering, body, claims and pass/drop reasons remain intact. Unmatched evidence remains verbatim. Initial draft prompts stay unchanged. The existing initial draft instructions already define source_line choices and semantic claim candidates; correction does not repeat those instructions.

## Alternatives and primary sources

Reordering review before claim validation would split the established validation pipeline. Adding persisted origin fields would change the ledger contract. Choosing any matching physical reference, silently dropping claims, weakening the critic or erasing rejected proposals would conceal the defect. Transient origin plus exact roundtrip checks preserves the existing authority and serialization boundary.

Three independent primary sources were checked on 2026-10-09: [Python JSON documentation](https://docs.python.org/3.10/library/json.html) establishes the supported JSON data representation; [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901) provides exact reference-resolution and error-handling principles; [Anthropic's context engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) discusses selecting useful context across repeated agent calls. Existing source_line IDs are not a new JSON Pointer implementation. These sources inform the approach; the repository's contracts, source trace and failing regressions establish the concrete defect and invariants. Python 3.10 compatibility is checked directly. No dependency or numerical limit is introduced.

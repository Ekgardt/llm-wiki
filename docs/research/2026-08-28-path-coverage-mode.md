# Покрытие по пути: «этот файл вообще проиндексирован?» с честным ответом

Дата: 2026-08-28. Пункт `CODE-05` единого бэклога — паритет с
`check_index_coverage` у codebase-memory-mcp, чей собственный дисклеймер
образцовый: «Coverage is best-effort, never proof of completeness», с явным
списком частично разобранных файлов.

## Вопрос

Отрицательный ответ инструмента («символ не найден», «мёртвого кода нет»)
стоит ровно столько, сколько покрытие индекса. Без проверяемого «этот путь в
поколении, свежий, узлов N» отрицание — догадка.

## Данные, измеренные на живом поколении

`source-manifest.json` активного поколения несёт 738 источников с
`relative_path` и `sha256` каждого. Узлы по пути считаются
`find_nodes(path=…)`; важно: его потолок строк ОТКАЗЫВАЕТ при переполнении,
а не режет молча (872 узла у `scripts/memory_queue.py` требуют потолка выше
запрошенного — измерено 2026-08-28, тот же голый `ValueError`, что уже
оформлен на границе инструмента).

## Решение

Режим `coverage` инструмента `get_architecture` (поверхность не растёт).
Новый модуль `scripts/path_coverage.py`:

- путь в манифесте источников? → `indexed`;
- sha файла сейчас против sha манифеста → `fresh` / `stale` / `missing`;
- число узлов по пути (потолок 10 000, при переполнении честное `>=`);
- идентификатор поколения — чтобы два ответа можно было сравнить.

Ответ повторяет дисциплину cbm: best-effort, не доказательство полноты, и
говорит это в самом ответе.

# Live claims re-read their source without reparsing every entry

On 2026-10-09 the real six-day compiler spent about 28 CPU minutes in its first 33 wall minutes, while fourteen model calls used 342 seconds. Its observer separately recorded hundreds of seconds in repeated refresh, claim assessment and rebuild phases. Those phases are nested and must not be added as independent totals.

A read-only profile of `ClaimIndex._collect_page` on one actual nine-claim page established a specific repeated cost: nine live evidence references caused nine complete `daily_entries` scans of the same source. Entry parsing accounted for 1.88 of 2.60 seconds in the initial profile. No model, knowledge or index writes were made. This demonstrates one root cause; it does not establish that every other compiler phase has the same cause.

The resolver now retains parsed entry groups and newline offsets for a physical daily path and its freshly verified content digest. Every lookup still performs the original protected stable read and hashes the current complete file. A changed digest replaces that path's entire parse map, including historical-part entries. Selection still checks the individual reference's block, byte boundaries and UTF-8 quote, then computes its quote and block hashes. Historical parts keep their existing complete search and hash qualification. Raw source byte objects are not retained by this new map. No persistent schema, runtime path, environment contract, dependency, daemon or numerical limit is introduced.

Alternatives considered: accepting file size or timestamps as freshness evidence was rejected because same-size edits with restored timestamps must be detected; reusing whole resolved claim results was rejected because different references must still validate their own block and span; snapshotting a source once for the whole rebuild was rejected because it would change the existing per-lookup live-read contract. Persistent parse caches and a second index would add invalidation and publication contracts unnecessarily. The existing uncached `_slice` remains necessary for archive resolution and explicit byte resolution without immutable reuse; it is not a parallel live implementation.

## Primary sources checked on 2026-10-09

- [Python 3.10 bytes documentation](https://docs.python.org/3.10/library/stdtypes.html#bytes-objects): immutable bytes and the baseline compatibility of this implementation.
- [NIST FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final): the existing SHA-256 integrity basis. NIST notes a planned revision; this change does not introduce a new algorithm or claim that the 2015 publication itself is new.
- [Maintained Linux stat manual](https://man7.org/linux/man-pages/man2/stat.2.html): filesystem metadata and its limitations. The choice keeps protected reads and actual content checks instead of treating metadata as content authority; Windows behavior requires its own platform checks.

The in-memory map trades entry/newline offset storage for avoiding repeated parsing. It lives only as long as the existing resolver and replaces old versions of each file rather than accumulating edits. Memory cost still depends on the actual evidence corpus; no arbitrary new bound is imposed. Direct regression and real-corpus measurements, rather than a generic cache recommendation, justify the choice.

## Evidence and qualification

Two new causal tests failed before correction: distinct live claims reparsed the same source, and a changed source was reparsed again for every reference. After correction the six new cases and unchanged resolver tests pass. They preserve per-lookup reads, detect same-size edits with restored timestamps, reject wrong blocks, reuse only verified historical parts, and compare every resolved field against uncached resolution for repeated block IDs and Unicode/CRLF sources. The related claim/compiler producer/contradiction set passed 107 tests; Python 3.10 passed 23. The additional compiler transaction/critic/packing and runtime deletion set passed 210 tests in 26.66 seconds. Actual AST/Lizard measurement covers twelve new or changed callables, maximum CCN 4, with no if-count or nesting violation. Ruff passes.

A paired real-page profile used the same page SHA-256 `5d20852fc0396cba54efb8f793e0d241efb0a5455249336a8cb4ec1a500377eb`. Original and corrected results share the exact row/diagnostic byte digest `2cf0ec7bebf6ea016fc3cecbc3bb53a22894a213d14caa6b08d580b56336d298`: nine rows, zero diagnostics. Original wall time was 2.946 seconds, corrected 0.563 seconds. Both performed nine protected live reads; complete entry scans fell from nine to one. These are profiled single-page measurements under a running compiler, not a full-cycle speed claim. Full installed-cycle, retrieval and platform qualification remain required before point 7 closes.

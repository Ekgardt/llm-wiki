# What an expired retrieval still owes the caller

2026-08-29. Research for the change that makes `retrieval.retrieve()` return
the legs that finished when the caller's deadline expires, instead of
discarding them. Measured on this machine unless marked otherwise; measured and
inferred are kept apart, and the negative results are reported first because
they are the important ones.

## The question

`retrieve()` runs its legs in sequence and calls `_check_stopped` between them —
seventeen sites whose whole purpose is to abandon work. When one fires, every
leg that had already completed is thrown away and the caller gets a
`TimeoutError`. The proposal was to hand those legs back instead, labelled
partial.

Two questions had to be settled. Is returning a partial answer the right
contract at all, or is it the silent-truncation failure that reviewers of other
systems keep objecting to? And does it move the number it was proposed to
move — `applied@5` 0.0 on the MCP path under load?

The first answer is yes, with a condition. The second answer is no, and the
measurement that says no also says what the real defect is.

## What practice does

Elasticsearch is the closest analogue and it has answered this question twice,
in both directions. Its default is a partial answer: when a shard exceeds the
search timeout the query is terminated early and the hits collected so far are
returned, with `timed_out: true` on the response rather than an error. The
same shape is offered deliberately as a choice — `allow_partial_search_results`
(cluster default `search.default_allow_partial_search_results`) lets an
operator turn the partial answer into a failure — and async search carries a
`partial_results` parameter for the same decision on a running query.
OpenSearch's asynchronous search inherits the shape: partial results enabled
means the response includes whatever hits and partial aggregations exist.

The objection is on the record too, and it is a good one. Elasticsearch issue
#27186 ("Throw errors on search timeouts") argues that most client applications
pay no attention to the flag and present partial results to the user with no
indication that they are incomplete; Grafana Loki #2999 is the same complaint
about a `200` carrying whatever was read before `querier.query-timeout`. The
danger named in both is not the partial answer. It is the partial answer that
*looks* complete.

gRPC's deadline guidance points the same way from the other side: deadlines
exist so that services can degrade gracefully — return partial results or
fallbacks — rather than hang, and both ends decide independently whether the
call succeeded, so a reply that arrives after the client's deadline is a reply
to someone who has already given up.

**What this settles.** Returning finished legs on expiry is the mainstream
contract, not an invention. The condition it comes with is that the answer must
say it is partial in a way the caller actually reads, and that no new work may
start after the deadline — otherwise the reply lands for a caller who has gone.

## What was implemented

`retrieve()` now carries a `_PlanProgress` while it runs. On a stop it returns
what is in hand: fusion, exact-filename promotion, page diversity and the cap,
all in-memory work over rows already paid for. No backend is called, the
reranker is not run, and no further stop check is made — this is the unwinding,
not more retrieval. The label is `partial=True` plus `fallback_reason` of
`deadline_expired_partial_result` or `cancelled_partial_result`, and
`effective_mode` / `signals_used` name exactly the legs that finished, so a
`HYBRID` request that only got its lexical leg reports `BASE` and `["lexical"]`.

Two boundaries were drawn deliberately.

*Only our own stop is salvageable.* A new `RetrievalStopped(TimeoutError)` is
raised by `_check_stopped`; a `TimeoutError` raised by a **backend** propagates
untouched. A backend timeout says the work failed. Ours says we stopped it, and
only the second leaves finished work behind. Without that split, the existing
tests that pin a legacy backend's timeout would have been silently converted
into partial answers.

*Nothing finished means nothing to hand back.* When no leg ran, the stop
re-raises. A result with no rows and no signals would be a refusal wearing the
clothes of an answer, which is the shape this vault has ruled against before.

The cost of the unwinding was measured rather than assumed, because the whole
defence of overrunning the deadline by it is that it is small. See the table
below.

## What was measured

Machine: 4 vCPU, live vault, generation `evidence-graph` active with
`vector_state: complete`, cross-encoder enabled by environment. Load was
generated by 14 CPU spinners; other agents were active throughout, which is the
condition the change was asked to address.

### 1. The paired stand: no effect, three rounds

One warm process, arms interleaved, toggled by replacing the salvage entry
point with one that re-raises — which is exactly what the stop path did before
this change, same checks in the same places. Everything else, including the
generation and the ranking, is identical between arms.

| round | arm | `applied@5` | `hit@5` | salvage entries | load |
|---|---|---|---|---|---|
| 0 | discard | 0.0 | 0.0 | 0 | 22.2 |
| 0 | salvage | 0.0 | 0.0 | 0 | 23.3 |
| 1 | discard | 0.0 | 0.0 | 0 | 22.2 |
| 1 | salvage | 0.0 | 0.0 | 0 | 22.5 |
| 2 | discard | 0.0 | 0.0 | 0 | 21.5 |
| 2 | salvage | 0.0 | 0.0 | 0 | 22.4 |

`grep_applied@5` was 0.1429 in all six. The decisive column is the last but
one: **the salvage path was entered zero times.** `retrieve()`'s stop path is
not what makes the loaded MCP call useless, so no change to it could have moved
this number.

### 2. What actually happens on the loaded MCP path

Fourteen calls through `mcp_server._search_vault`, load 14–18:

    rows=1  6.0–8.8 s  err=None  partial=True
    fallback_reason=optional_stage_timeout  effective_mode=BASE

Not zero rows and not an exception: **one row**, every time. The earlier
reading that ten seconds "returned no rows at all" is a description of the
stand's score, not of the call.

Instrumented inside the leg, three cases, all identical:

| step | rows | seconds |
|---|---|---|
| `_exact_filename_rows` | 0 | 0.16–0.23 |
| `_generation_matched_rows` (the BM25 `MATCH`) | **1** | 0.00–0.01 |
| `_deduplicated_results` | 1 | 0.00 |
| `_generation_fts_search` | 1 | 0.17–0.23 |
| `_filtered_hits` (limit 40) | 1 → 1 | — |

Nothing truncates. The SQL returns one row for a request of forty, in ten
milliseconds. Quiet, the same call returns five good rows with
`effective_mode=HYBRID`.

And the one row is not a real page. The budget sweep below counts paths *after*
the stand drops its own answer sheets, and it counts zero every time while the
raw call returns one — so the single BM25 row is the sheet
(`benchmark/vault-application-v1.json`), which contains each question verbatim
and is therefore the one document in the corpus that a BM25 match on that
question can find.

**So the defect is the opposite shape from the one this change addresses.** The
mandatory lexical leg finds nothing usable on these questions — they are
Russian and most of the corpus is English, which is the whole reason this vault
adopted a multilingual embedder in the first place (`NEW-60`, 2026-08-23). All
the retrieval quality comes from the *optional* dense leg. When the budget
policy abandons dense under load, the answer collapses to that single sheet row
and `applied@5` goes to 0.0. The work being lost is not work that finished; it
is work that was never allowed to start.

Recorded, not fixed: **the signal-bearing leg is the optional one.** Any real
cure for the loaded MCP number is a change to which leg is mandatory, or to
what the optional-stage policy will spend on it — a different decision from
this one, and one that needs its own note. It is also worth saying plainly that
the reading this change was commissioned from — "ten seconds produced no rows
at all" — is a description of the stand's score, not of the call, and the
difference is exactly what hid the real defect.

### 3. Where the stop path is reached on the MCP wrapper: nowhere

`MCP_OPERATION_SECONDS` is the whole operation's budget and a dispatcher that
has already spent part of it hands `_search_vault` less, so the remaining
budget was swept. Paired arms, one warm process, two rounds, load 17.5–24.5,
seven cases each:

| budget | arm | raises | rows after dropping sheets | salvage entries |
|---|---|---|---|---|
| 6 s | discard | 6, 6 | 0 | 0 |
| 6 s | salvage | 6, 7 | 0 | 0 |
| 8 s | discard | 3, 4 | 0 | 0 |
| 8 s | salvage | 2, 3 | 0 | 0 |
| 10 s | discard | 1, 0 | 0 | 0 |
| 10 s | salvage | 0, 0 | 0 | 0 |

Every single raise originated at `retrieval._check_deadline`, and the salvage
entry point was called **zero times in all twelve runs**. The two facts
together locate it: the stop that fires is the one *before* the plan — either
`retrieve()`'s entry check or `retrieve_via_search_memory`'s own — because on
this path the budget is consumed by catalog validation, generation resolution
and the consumption seal before any leg starts. At that point nothing has
finished and re-raising is the only truthful answer, which is what the code
does.

The arm difference in the raise counts is noise, not signal: the same arm gave
6 and 7 at 6 s and 2 and 3 at 8 s. This vault has already recorded that stand
numbers taken while something else runs wander by a case or two, and these
wander by exactly that.

### 4. The unwinding is cheap

`retrieve()` driven to expire immediately after a lexical leg of a given pool
size, twenty samples each, quiet machine:

| lexical pool | salvage p50 | max |
|---|---|---|
| 25 rows | 0.4 ms | 0.7 ms |
| 100 rows | 1.4 ms | 1.4 ms |
| 200 rows | 2.7 ms | 2.8 ms |
| 400 rows | 5.4 ms | 8.7 ms |

Timed from the moment the leg handed its rows back, so the leg's own cost is
excluded; load average 17–20 during the run, which makes these upper bounds
rather than best cases. The real pool on this vault is 40. Against a measured
mandatory tail of 0.59–0.86 s and an optional-stage wait overshoot of up to
0.9 s, an unwinding of a few milliseconds is not what makes a caller late.

### 5. The direct path is untouched

The operator's path passes no deadline, so the stop path cannot fire on it and
the numbers must be identical rather than merely close. Paired, interleaved,
one warm process, two rounds, quiet machine (load 4.3–6.8):

| round | arm | `applied@5` | `hit@5` | `hit@1` | salvage entries |
|---|---|---|---|---|---|
| 0 | discard | 0.8571 | 0.8 | 0.4 | 0 |
| 0 | salvage | 0.8571 | 0.8 | 0.4 | 0 |
| 1 | discard | 0.8571 | 0.8 | 0.4 | 0 |
| 1 | salvage | 0.8571 | 0.8 | 0.4 | 0 |

`grep_applied@5` 0.1429 throughout. Both stand gates pass on both arms.

## What was decided

Return the finished legs, labelled, and keep raising when nothing finished.

The deadline is not weakened by this and that is the point worth being precise
about. By the time a stop check fires after a leg, the overrun has already
happened — the leg returned when it returned, and `retrieve()` never had the
power to make it return sooner. The choice at that instant is not "on time or
late". It is "late with an answer" or "late with an exception". Raising does
not give the caller its time back; it only adds the loss of work already paid
for. What must stay true, and is enforced, is that no *new* work starts after
the stop: no backend call, no reranker, no second window.

Rejected: giving the lexical retry in `mcp_server._search_vault` a fresh
window. That would land a reply after the caller's deadline for a caller who
has given up, and two tests pin the opposite —
`test_search_vault_reuses_caller_operation_deadline` and
`test_search_vault_degrades_after_delayed_optional_initialization`. The retry
keeps the caller's own deadline and is therefore usually dead on arrival; that
is honest, and it stays.

Rejected: making salvage opt-in behind a parameter. Every real caller would
pass it, which makes the default a lie about what the product does, and the
one caller that would not pass it is a test.

Accepted cost, named: two tests that pinned "abandon" now pin "hand back". Both
were rewritten rather than deleted, and both still assert the half that has not
changed — that the check fires where it fired and that nothing further runs.

**The uncomfortable part, said plainly.** Across every real path measured
today — the MCP wrapper at 6, 8 and 10 second budgets under load 17–24, twelve
paired runs, and the operator's CLI path which passes no deadline at all — the
salvage entry point was reached **zero** times. It fires in constructed tests
and nowhere that was observed in the product. Five callers pass a deadline into
retrieval (`mcp_server` twice, `query_memory`, `mcp_http`'s warmup, and
`search_memory.search` itself); only a caller whose budget expires *between*
two legs can reach it, and on this vault the budget is far more likely to be
gone before the first leg than between the first and the second.

So this is a correctness change with no demonstrated effect. It costs nothing
measurable, it removes a way of losing work that would otherwise be silent when
it does happen, and it must not be described as the fix for `applied@5` 0.0.
The fix for that is section 2.

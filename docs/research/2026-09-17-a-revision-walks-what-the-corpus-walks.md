# A revision walks what the corpus walks, and git's word is checked against the disk

Dated 2026-09-17. Third audit: the second half of G-H3, and G-M8 points 1 and 2. The
research before the fix.

Files: `scripts/corpus_snapshot.py`, `scripts/workspace_revision.py`,
`tests/test_a_revision_walks_what_the_corpus_walks.py`.

## What was found

- **The walk (G-H3, second half).** `_relevant_files` descends into every directory except
  `.git`. On this checkout that means about 10 800 ignored `.py` files under `.venv` are
  hashed on every full compute and counted against `MAX_REVISION_FILES` (100 000). The
  corpus walk that builds the generation prunes them: `corpus_snapshot._always_pruned_name`
  refuses `__pycache__` and every hidden name in every repository. So the freshness proof
  covered files the thing it proves fresh has never seen. A checkout with a large ignored
  tree (`node_modules` under a hidden directory, several virtual environments) can exceed
  the entry ceiling and be refused a revision altogether.
- **G-M8 point 1.** `_status_paths_all_expected` requires every path git reports as changed
  to be an entry of the stored revision, but `_add_status_entry` drops a status path that
  is not a regular file: a nested untracked repository (git reports `nested/`), a symlink
  that is not in a relevant place. The next verification then finds a status path that is
  not in the entries and answers "changed" — for ever, on every query, each answer paying a
  full recompute. Reproduced: a checkout with a nested git repository verifies `False`
  twice in a row with nothing touched in between.
- **G-M8 point 2.** `git rm --cached` of a tracked file that `.gitignore` also names leaves
  git reporting `1 D.` for a path whose file is still on disk. `_add_status_entry` records
  it as `deleted` with no path; the walk then finds the same file and `_add_relevant_file`
  attaches the path to that record, keeping git's kind. The result is an entry of kind
  `deleted` carrying a digest and a non-zero size — which the module's own
  `_require_valid_entry_digest` rejects, so the revision it just built cannot be verified.
  Reproduced: `('cached.py', 'deleted', 6)`.

## Practice on this date

- Pyright's configuration documentation: "By default Pyright also excludes the following:
  `**/node_modules`, `**/__pycache__`, `**/.*` (hidden directories)"
  (https://raw.githubusercontent.com/microsoft/pyright/main/docs/configuration.md, fetched
  2026-09-17). The language server this revision exists to keep honest ignores hidden
  directories itself. `node_modules` is left alone here on purpose: pruning it would change
  what the corpus collects in every repository, which is a separate decision.
- Git status porcelain v2: an ordinary changed entry carries `<XY>`, where `X` is the index
  state and `Y` the worktree state (https://git-scm.com/docs/git-status). `D.` is "deleted
  from the index, unchanged in the worktree" — the worktree file exists. The module folds
  both letters into one word (`_status_change_kind`), which is where a staged deletion of a
  file that is still on disk turns into "deleted".

## The decisions

1. The revision walk prunes the directory names the corpus walk always prunes:
   `corpus_snapshot.always_pruned_directory_name` (generated bytecode and every hidden
   name) becomes public and both walks call it. `.git` stays pruned by the same rule, since
   it is hidden. One definition: a revision that covered more than the corpus could not
   make the corpus fresher, only slower.
2. A status path that a compute would not record is not evidence of a change:
   `_status_paths_all_expected` asks the same question the compute asked
   (`_status_entry_stat`) before it calls a missing entry a mismatch. A path that has gone
   missing, or that the compute would refuse, still counts as a change.
3. Git's word is checked against the disk: a status of `deleted` for a path that is still a
   regular file is recorded as `index-deleted` — an entry that carries a digest like any
   other and whose verification requires git to keep reporting `deleted`. The `deleted`
   kind keeps its meaning (no digest, size 0, the file is gone) and the consistency fence
   that re-checks deletions is unchanged.

`index-deleted` is a new entry kind. Revisions are computed and verified in one process and
are never stored in a tracked artifact, so no migration exists to write.

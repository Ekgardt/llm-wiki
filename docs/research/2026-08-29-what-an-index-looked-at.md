# What an index looked at

One-sentence summary: a whole-repository index owes three things its caller
cannot otherwise learn — that a root may be a *file*, that a prune list is
project vocabulary and must not travel to other repositories, and that
"indexed" is not "tracked" unless the receipt says so.

Dated research for the three gaps commit `27301e1` named and did not take.
Measurements in this note were taken on this machine on 2026-08-29 against
`/home/user/llm-wiki` and `/home/user/agenticos/checkout-claude/main`.

---

## 1. The three questions

Commit `27301e1` made the code index cover a repository of any layout: roots
come from what Git tracks, minus what the corpus walk prunes. Its author named
three remainders.

1. `tracked_top_level_directories()` returns only directories, so a tracked
   file at the repository root is never indexed.
2. `SKIP_DIRECTORIES` — `gaps`, `raw-sources`, `_template` — is this vault's
   own vocabulary, applied inside every code root of every repository.
3. The walk under a root is a filesystem walk, not a Git listing, so untracked
   files under a tracked root are collected.

Each is the same defect class: an answer that cannot say what it looked at.

---

## 2. What practice does

### 2.1 A root may be a file, and root files are where the answers are

No mainstream indexer treats "the repository" as "the repository's
subdirectories". ripgrep's default unit is the path, and the only things it
drops without being asked are binary files, hidden files, and whatever the
repository's own ignore files exclude — never "a file at the top level"
([ripgrep GUIDE][rg-guide]).

Measured here, the top-level tracked files are exactly the files a question
about a repository is most likely to be about:

| repository | tracked root files | after hidden are pruned |
|---|---|---|
| `llm-wiki` | 17 | 12 — `AGENTS.md`, `CHANGELOG.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `LICENSE`, `README.md`, `README.ru.md`, `README.zh-CN.md`, `install.ps1`, `install.sh`, `pyproject.toml`, `uv.lock` |
| `agenticos` | 11 | 7 — `README.md`, `bootstrap.sh`, `crontab.txt`, `env.template`, `onboarding.md`, `pyproject.toml`, `uv.lock` |

The audit entry says "seven names here and as many there". The seven for the
neighbour is right; here it is twelve. Corrected by measurement, not argued.

The fix is already available and needs no new walk: `corpus_snapshot`'s
`_add_code_root` branches on `stat.S_ISDIR` and calls `discovery.add()` for a
regular file. A code root has been allowed to be a file since the collector was
written; only the *discovery* step insisted on directories.

### 2.2 A prune list is either universal or repository-local — never one project's nouns

ripgrep separates the two cleanly. Universal defaults (hidden, binary) are
compiled in; everything else comes from files that live *in the repository
being searched* — `.gitignore`, then `.ignore`, then `.rgignore`, each
overriding the last ([ripgrep GUIDE][rg-guide], [ripgrep README][rg-readme]).
The distinction is the whole design: ripgrep does not carry one project's
directory names into another project's tree.

`SKIP_DIRECTORIES` mixes the two categories in one frozenset:

- `__pycache__` — generated bytecode. Universal for any repository containing
  Python. Belongs with the compiled-in defaults.
- `gaps`, `raw-sources`, `_template` — this vault's knowledge layout. `gaps` is
  an OKF page type (`CLAUDE.md` §5); `_template` is a project scaffold;
  `raw-sources` is a knowledge directory name. None of the three is a fact
  about repositories in general.

Measured, so the cost of leaving it alone is known and the cost of changing it
is known:

- Under this vault's own approved code roots the only pruned directory that
  exists is `__pycache__` (4 of them). `gaps`, `raw-sources` and `_template` do
  not occur under any code root.
- `_template` does occur, once, at `knowledge/projects/_template` — reached by
  the *knowledge* walk, not the code walk.
- The neighbouring repository has no directory of any of the three names.

So today nothing is lost by the vault vocabulary travelling, and nothing is
lost by stopping it. What changes is the failure mode: a foreign repository
with a top-level or nested `gaps/` directory currently loses it with no
refusal, no `excluded_roots` entry and no line in the receipt. That silence is
the shape of `NEW-67` and `NEW-135`, both of which this vault has already ruled
against.

### 2.3 "Indexed" is not "tracked", and the honest answers are a listing or a receipt

The strongest current argument for a Git listing is bounding, not correctness:
a filesystem crawler walks whatever is on disk, so a missing or incomplete
`.gitignore` sends it into `node_modules`, caches and build output, and on a
200k-file repository it OOMs; `git ls-files` "only returns tracked files, so
the result set is always reasonable regardless of what's on disk"
([qwen-code #3137][qwen]). Sourcegraph's zoekt indexes from the Git object
store for the same reason ([zoekt][zoekt]).

That argument is weaker here than it is there, because this collector is
already bounded by construction — `max_files`, `max_entries`,
`max_directories`, `max_depth`, `max_file_bytes`, `max_total_bytes`, plus a
deadline — and it prunes hidden directories, which is where the crawler
disasters in that issue live.

The other half of practice is the one this vault has already adopted from
Sourcegraph in the `27301e1` decision: state the omission at the moment it is
made. Cursor reached the same place from the product end — its 2026 indexing
settings carry a "View included files" view, because an index whose contents
cannot be enumerated cannot be trusted or debugged
([Cursor indexing guide][cursor]).

Measured, the difference between the two policies on the only two repositories
available:

| repository | untracked files collected under tracked roots | of those, outside `__pycache__` |
|---|---|---|
| `agenticos` | 17 | **0** |
| `llm-wiki` | 3 | **3** — `benchmark/code-parity-2026-08-29-anchored-run1.json`, `…-run2.json`, `benchmark/flush-classification-live.json` |

So on the foreign repository a Git listing would change nothing at all: every
untracked file under a tracked root is inside `__pycache__`, which the walk
already prunes. On this vault it would *remove three real sources* — live
benchmark results that are legitimately part of what the vault indexes about
itself, written by a benchmark run that has not been committed yet.

## 3. What follows

**Gap 1 — fix.** Discovery returns tracked top-level *entries*, files included.
Hidden root files (`.gitignore`, `.python-version`, …) are pruned by the same
one rule that prunes hidden directories, so they appear in `excluded_roots` and
are named rather than dropped. No new prune rule, no new walk.

**Gap 2 — fix, split by kind.** `__pycache__`, hidden names and the archive
names keep pruning everywhere. The three vault nouns prune only on the walks
that read this vault's knowledge tree. A code walk — this vault's own included
— stops applying them. Measured above: this changes nothing in either
repository today, and removes a silent loss that has no refusal attached to it.

Archive names (`archive`, `.archive`, `_archive`) are deliberately *not* moved.
They are not vocabulary: they are governed by `include_historical`, which is a
policy switch a caller sets, and they carry the same meaning in any repository.

**Gap 3 — refuse the walk change, state it in the receipt, with a number.**
Making the walk agree with Git would remove three real sources from this
vault's own corpus, would put a `git` subprocess inside a sealed traversal that
today makes none, and would change nothing on the one foreign repository
available to measure. Against that, the defect is real but is a *reporting*
defect: the receipt does not say which it did.

So the receipt says it, and says it with a measured number rather than a label:
`"source_selection": "filesystem-walk"` names the policy, and
`"untracked_sources": N` counts the collected sources Git does not track.
`N == 0` is the common case and is worth being able to see; `N > 0` is exactly
the condition a reader needs to know about, and it is now countable instead of
inferable. The receipt is `repository_index`'s own return value, not the corpus
policy, so `NEW-81` does not apply and no published generation is invalidated.

**`excluded_roots` in `list_repositories` — left alone, and here is why.** The
listing reconstructs a generation's coverage from `source-manifest.json`'s
recorded `policy.code_roots`. `excluded_roots` is not recorded anywhere a
listing can read: the index receipt is returned to the caller and never
persisted, and adding the field to the policy is the schema change that
invalidates every published generation (`NEW-81`). It *could* be recomputed by
asking the checkout for its tracked top-level entries at listing time — but
that answers a different question ("what would be excluded now") than the one
asked ("what did this generation exclude"), and the checkout may have moved,
changed or gone. A field that quietly answers a different question is the
defect this whole note is about, so it stays out.

# Перезапуск, до которого не дотягивается обработчик — 2026-09-06

Найдено при разборе 23 застрявших классификаций сессий. Один дефект исправлен,
второй описан и **намеренно не тронут** — объяснение ниже.

## Что было

23 задачи `flush` стояли в состоянии `ready` с `attempts=8` при пределе 8.
Работник их не берёт: бюджет исчерпан. `redrive` их не берёт: он требует
состояния `dead`. Никто больше на них не смотрит.

Причина: `_failure_state` при обычном отказе всегда возвращал `ready`, не
глядя на счётчик попыток. Путь истёкшей аренды это правило имел с самого
начала, путь отказа — нет. **Исправлено** (`46957fb`), плюс
`scripts/repair_exhausted_queue_tasks.py` для тех, кто уже застрял.

## Что осталось

После почина 23 задачи стали `dead`, `redrive` их принял и создал 23 новых.
Но ни одна не была обработана.

`redrive` копирует задачу и не копирует строку `capture_task_links`. А
`claim_capture` выбирает только задачи, у которых такая строка есть:

```sql
FROM tasks AS task
JOIN capture_task_links AS link ON link.task_id = task.id
WHERE task.state='ready' AND task.kind='flush' ...
```

Значит перезапущенная задача захвата недостижима для обработчика захвата
навсегда. А `ready_capture_intents_without_task` — тот самый подметальщик,
который выдаёт задачу намерению без задачи, — ищет `link.intent_id IS NULL`,
то есть намерение с *мёртвой* задачей орфаном не считает.

Две дыры смыкаются: намерение с мёртвой задачей нельзя ни усыновить, ни
перезапустить.

## Почему не исправлено сегодня

Ссылка задачи на намерение создаётся только через `enqueue_capture`, который
требует живой `IntentFence` и владельца роли `capture`. Это тот самый
«единый огороженный реестр допуска» из контракта в `CLAUDE.md`. Подделать
строку связи в обход ограды — значит обойти ограду. Ослабить правило
усыновления до «нет живой задачи» — значит на каждом проходе работника
создавать новую задачу для намерения, которое умирает снова, то есть менять
одну утечку на другую.

Правильное решение требует проектного выбора: сколько вторых шансов у
намерения и кто их считает. Это решение владельца, а не правка на ходу.

## Цена сейчас

Ноль потерянных сессий. Разговоры этих 23 сессий лежат в
`knowledge/raw/sessions/` по решению `session-evidence-retention-decision` —
они на диске и находятся `grep`. Не хватает только сжатого блока в дневнике.

Новые сессии не попадают в эту дыру: классификатор больше не слепой, и
задачи перестают исчерпывать попытки на пустом месте.

23 перезапущенных задачи отменены, чтобы не изображать очередь работы,
которую никто не возьмёт.
